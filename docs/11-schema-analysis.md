# Schema Analysis

This document provides a deep-dive analysis of all the schema definitions across the project, evaluating their usage, validation rules, consistency, and adherence to industry best practices.

## 📍 Schema Locations

### 1. Zod Validation Schemas
- **Location**: `src/pages/Auth.tsx`
- **Schemas Identified**:
  - `signInSchema`: Validates email (format) and password (minimum 1 character).
  - `signUpSchema`: Validates email (format), password (minimum 8 characters), and fullName (minimum 2 characters).
- **Note**: Zod is installed in the project (`package.json`), but these are the *only* Zod schemas defined in the codebase.

### 2. API / Type Schemas (Supabase)
- **Location**: `src/integrations/supabase/types.ts`
- **Schemas Identified**: Auto-generated TypeScript definitions for the entire Supabase PostgreSQL database schema. It dictates the API schema used by `@supabase/supabase-js` to strictly type database queries, inserts, and updates for the frontend.

### 3. ORM, GraphQL, Prisma, Drizzle, Mongoose
- **Status**: **None found.**
- **Details**: The project relies entirely on Supabase's PostgREST API (typed via `types.ts`). There is no Node.js backend using an ORM like Prisma or Drizzle, no MongoDB (Mongoose), and no GraphQL endpoint. (A Python backend `app/` is referenced in scripts, but the directory is missing from the repository, meaning no SQLAlchemy or Pydantic schemas are present).

## 🔍 Schema Analysis

### Validation & Missing Validation
- **Current State**: Validation is effectively implemented for Authentication, providing immediate frontend feedback for invalid emails or short passwords.
- **Missing Validation**: There are *no validation schemas* for any of the other critical data entry points in the app (e.g., creating tasks, onboarding/user calibration, creating projects, logging habits). These forms appear to rely on raw React state and backend database constraints (like `CHECK` constraints) rather than proactive client-side Zod validation. This leads to a degraded user experience if an invalid state is submitted to the API.

### Naming & Consistency
- **Naming**: The Zod schemas (`signInSchema`, `signUpSchema`) are named logically and contextually. The API types generated by Supabase (`Database['public']['Tables'][...]`) follow standard Supabase conventions.
- **Consistency**: **Low**. The project mixes validation strategies. Auth uses strict Zod validation, while the rest of the application seems to forego schema-based validation entirely.

### Reusability
- **Poor Reusability**: The Zod schemas are defined directly inside `src/pages/Auth.tsx`. This couples the validation logic tightly to the UI component. If you needed to validate user creation via an admin panel or a separate modal, the schema could not be reused without duplicating the code.

### Duplicate Schemas
- None identified. `signInSchema` and `signUpSchema` share the `email` validation rule, which is standard, though extracting a shared `emailSchema` could be a minor optimization.

### Best Practices Evaluation

**What the project does well:**
- Utilizing Supabase's generated `types.ts` is an excellent practice that ensures frontend API calls are strictly typed and synchronized with the actual database schema.

**Areas for Improvement (Violations of Best Practices):**
1. **Extract Validation Logic**: Zod schemas should be extracted from component files (`Auth.tsx`) and placed into a dedicated directory like `src/lib/validations/auth.ts`.
2. **Universal Schema Adoption**: Zod (combined with `react-hook-form` and `@hookform/resolvers/zod`, both of which are mysteriously present in `package.json` but largely unused) should be adopted universally for all forms in the application (Tasks, Projects, Habits, Settings). 
3. **Shared Base Schemas**: Common fields (like `email`, `password`, `uuid`) should be defined as base schemas and composed together to dry up the validation logic.
